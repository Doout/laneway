# Local daemon API v1

This document defines the compatibility boundary between a Laneway endpoint
client and `lanewayd`. The Go and Rust daemons implement the same bounded
HTTP/1.1 API on a Unix-domain socket. The default socket path is
`/run/laneway/lanewayd.sock`.

The keywords **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are normative.

## Security boundary

The daemon MUST create the socket with mode `0600`, and MUST refuse to replace
a path that is not a Unix socket. The socket owner is the authenticated local
principal: only a process running as that same operating-system account may
use this API. Request headers and JSON fields do not provide authentication.

Clients MUST NOT treat `daemon_instance_id` or a request ID as a credential.
Expanding access to a group, another local user, TCP, or a browser origin needs
a separately designed authenticated broker and is outside this contract.

## Transport and bounds

- Requests use HTTP/1.1 over the protected Unix socket.
- A request header is limited to 8 KiB. Any request body is limited to 4 KiB,
  uses `Content-Length`, and does not use transfer encoding. The only route
  that consumes a body in v1 is `POST /v1/exit`.
- A client MUST reject a response larger than 1 MiB.
- Responses use `Cache-Control: no-store`.
- Buffered JSON responses include an exact `Content-Length` and MUST NOT use
  chunked transfer encoding.
- JSON is UTF-8. Successful JSON responses end with a newline; clients MUST
  not depend on whitespace or object member order.

## Compatibility rules

Request objects are strict. Field names use exact lowercase spelling. A daemon
MUST reject unknown or duplicate members, case variants, null or incorrectly
typed known values, malformed JSON, or trailing JSON values with
`400 invalid_request`.

An enabled Exit selection requires a canonical, nonzero 128-bit node ID in
exactly 32 lowercase hexadecimal characters. A disabled selection requires
`selected_node_id` to be omitted or empty. Validation happens before the Exit
callback is invoked.

The shared accepted and rejected request cases are recorded in
[`testvectors/local-api/exit-selection-v1.json`](../testvectors/local-api/exit-selection-v1.json).

Response objects are additive. A v1 client MUST ignore unknown response
members, including unknown members of nested objects, while continuing to
validate the exact spelling, non-null type, uniqueness, and meaning of every
known member it uses. A case variant of a known member is not an alias. A
daemon MUST NOT remove a documented v1 member or change its meaning under
`/v1`.

`GET /v1/status` includes:

- `daemon_instance_id`: a nonzero 128-bit value encoded as exactly 32 lowercase
  hexadecimal characters. It is generated by the API server at startup and
  remains stable until that server stops. A changed value means the daemon API
  restarted; an unchanged value does not imply that connection state is
  unchanged.
- `api_revision`: an unsigned integer describing the minimum documented
  additive v1 response shape. This document defines revision `1`. It is not a
  status generation, configuration epoch, or product build number.

Older v1 daemons may omit these additive members. A tolerant client will then
decode an empty instance ID and revision `0` and MAY present reduced restart
detection. The canonical revision-1 status document is
[`testvectors/local-api/status-v1.json`](../testvectors/local-api/status-v1.json).

## Request correlation and errors

Every response produced by a routed v1 request MUST include
`X-Laneway-Request-ID`. HTTP parser failures may close the connection before a
request reaches v1 routing. The ID is generated by the daemon, ignores any
client-supplied value, and contains exactly 32 lowercase hexadecimal
characters. Except for the body-free response required by HTTP for `HEAD`,
every routed error response has content type `application/json` and the same ID
in this envelope:

```json
{
  "request_id": "0123456789abcdef0000000000000001",
  "code": "invalid_request",
  "detail": "invalid exit selection",
  "retryable": false
}
```

`code` and `retryable` are stable machine-readable fields. `detail` is for a
person, is bounded to 2 KiB of UTF-8, and MUST NOT be parsed. The v1 codes are:

| HTTP | Code | Retryable | Meaning |
| ---: | --- | :---: | --- |
| 400 | `invalid_request` | no | The HTTP or JSON request is invalid. |
| 404 | `not_found` | no | The path is not a local API route. |
| 405 | `method_not_allowed` | no | The route does not support the method. |
| 409 | `conflict` | no | Current daemon or controller state rejects the requested change. |
| 501 | `unsupported_operation` | no | This daemon has no implementation configured for the operation. |
| 503 | `busy` | yes | The bounded server has no request capacity. |
| 500 | `internal` | yes | The daemon could not produce a valid response. |

The canonical envelope is
[`testvectors/local-api/error-v1.json`](../testvectors/local-api/error-v1.json).
Clients MUST reject an envelope with missing, null, duplicated, or incorrectly
typed known members; a malformed request ID; a header/body request-ID mismatch;
or a status, code, and retryability combination different from the table.

## Routes

| Method and path | Success | Contract |
| --- | --- | --- |
| `GET /v1/status` | `200` JSON object | Daemon, connection, lease, carrier, route, metrics, Exit, and controller status. |
| `GET /v1/peers` | `200` JSON array | Current peer identities, prefixes, and selected paths. |
| `GET /v1/routes` | `200` JSON array | Current installed route prefixes, next-hop nodes, and kinds. |
| `POST /v1/exit` | `204` empty | Strict `{"enabled": boolean, "selected_node_id"?: string}` selection. Existing Exit validation and persistence rules apply. |

Methods are exact: `HEAD` is not an alias for `GET`. Paths are matched without
redirect-based cleaning, so duplicate slashes and dot segments do not resolve
to a v1 route. Query strings are not part of this API and are invalid requests.
`GET` requests with bodies are invalid. A `HEAD` error preserves the JSON
envelope's `Content-Length` but does not transmit that body.

The response members that predate revision 1 retain their existing names and
semantics; the golden fixture records their common Go/Rust JSON shape.

Profile storage, login, logout, connect, disconnect, update installation, and
diagnostic-bundle operations are intentionally not part of this foundation.
They require explicit ownership, credential, cancellation, and privilege
semantics before routes are added.
